### Step 2: gate 3.4

A fresh session in A, whose queue held one open note, was asked
"what's parked?".

- Calls, in transcript order: `Skill` with `laterbox:notes`, then
  `mcp__laterbox__queue` with `{"action":"list"}`. There was no
  `ToolSearch` call. The tool's result was the listing:
  `tmp.ciYT96rYYE: 1 parked` / ` 1. renew the staging certificate (today)`.
- No permission dialog was shown for `mcp__laterbox__queue`. The debug log
  records the hook serving the call before Claude Code's own steps:
  "laterbox (user) answered tool.call without next() in 31.4ms; nothing
  beneath it ran for this dispatch" and "tool.call mcp__laterbox__queue
  ...: resolved by a hooks module (result)". No permission line names the
  tool.
- The tool was listed in the prompt, not deferred:
  "mcp__laterbox__queue visible after 201ms" at session start and
  "Dynamic tool loading: 0/84 deferred tools included" on each request.
- The skill loaded before the call. Loading it showed Claude Code's
  skill-invocation prompt, "Use skill "laterbox:notes"?", answered with the
  one-time "Yes"; the skill then reported "Successfully loaded skill · 1
  tool allowed". Its `allowed-tools` line names the tool, so this run alone
  cannot tell the skill's pre-approval from the module serving the call;
  the debug line above shows the call never reached the permission step.
- In Step 4's session the model answered a second "what's parked?" by
  calling the tool directly, without loading the skill again, and no
  dialog was shown either.

Verdict: pass. The model called the tool with no permission dialog and no
tool-search step. The skill-invocation prompt that came before the call is
recorded as observed and is not counted: spec 3.4, as corrected in commit
94905ee, says Claude Code's own skill-invocation prompt, which every plugin
skill gets in the `default` permission mode, is not the dialog the gate
means. The prompt came from the model loading the skill first, as the
account's user-level instructions ask for a listing (see Method). Step 4's
second ask called the tool with no new skill load (the skill had been
loaded earlier in that session) and showed no dialog. Gate 3.4 passes on
Linux, and by the decision of 2026-11-06 the skill ships naming only the
tool, without the Bash fallback of spec 3.4.

Evidence: `step2-tool-uses.jsonl`, `step2-debug-excerpt.txt`,

#### Deny run

A fresh session in A, whose `.claude/settings.json` held exactly
`{"permissions":{"deny":["mcp__laterbox__queue"]}}`, was asked
"what's parked?".

- Claude Code read the rule ("Adding 1 deny rule(s) to destination
  'projectSettings': ["mcp__laterbox__queue"]") and kept the tool out of
  the session: "mcp__laterbox__queue registered; a deny rule withholds it
  from this session's tools, so not waiting for it to list".
- Calls, in transcript order: `Skill` with `laterbox:notes` (after the
  same skill-invocation prompt), then `ToolSearch` with
  `select:mcp__laterbox__queue`, which answered "No matching deferred tools
  found", then a `Bash` call `ls -la ~/.local/bin/later 2>&1; later 2>&1`.
  The model said "The laterbox MCP tool is not registered in this session,
  so I'll reach the same queue engine through its terminal entry point."
- The `Bash` call asked for permission and was declined, so nothing ran.
  The tool was never called and no hook of the module ran for it.

Verdict: pass of spec 3.5 as corrected in commit 94905ee. Claude Code
2.1.318 honours a deny rule for the tool itself, before any call, by
withholding the tool from the session's tools, as the corrected spec
says, and a deny rule is the way to block the tool. This
run was first recorded here as a fail, judged against the earlier wording
of spec 3.5 ("a permission rule the user wrote for the tool, allow or
deny, is not consulted", with a worked example in which a user with a deny
rule still gets the listing). That wording was in error, and 94905ee
corrects it. The README's "a deny rule does not stop it" (README.md line
263 at 460cc08) carries the same error.

With the tool withheld, the model, right after the skill loaded, took the
terminal route that the skill's background section names: the command
`later` and the link `~/.local/bin/later` (skills/notes/SKILL.md lines 85
to 87 at 460cc08), the exact command and path of its `Bash` call. The
account's user-level instructions (see Method) name the same command, a
second source for that choice. That route carries no text guard:
`later done <n>` and `later drop <n>` take the note's number alone, with
no `--if`, so the guard of spec 3.2 does not protect it. On native Windows
the terminal command does not exist. The deny rule was removed before
Step 3.

This run raised two items, both decided on 2026-11-06:

1. The deny rule: a deny rule for the tool withholding it from the session
   is Claude Code's own block and the intended behavior. Spec 3.5 and R7
   are corrected in commit 94905ee; the README's deny-rule sentence is
   corrected later in this release.
2. The skill when the tool is withheld, including its terminal-route line:
   the skill tells the user the tool is not in the session and runs the
   engine no other way, and its line about the terminal command states
   what the user can run, not a route for the model (spec 3.3 as corrected
   in 94905ee). The skill's text is corrected later in this release. No
   Bash fallback is added: gate 3.4 passed on Linux, and the skill ships
   without it.

Evidence: `step2deny-tool-uses.jsonl`, `step2deny-debug-excerpt.txt`,
`step2deny-skill-dialog-screen.txt`, `step2deny-bash-fallback-screen.txt`,
`step2deny-after-screen.txt`.

### Step 5: idle pane

A fresh session in A, started with `--debug` (and `--debug-file`) under
`strace -f --seccomp-bpf -tt -qq -e trace=execve`. A bare `/later` opened
the pane on A's queue (3 open notes) at 20:23:39.8; nothing else was typed
until 20:26:07.4, 147.5 seconds after the open's read. The queue file's
modification time stayed 00:20:03 local throughout.

Counting method: the debug log's `$.process.run (laterbox): ...later.sh
with 1 args` lines, cross-checked with the trace's processes whose
`later.sh` argument vector ends in `rows`. Both give the same four runs
(the trace's other `later.sh` processes are the session-start hook's
shell and bash, started before the pane opened).

| Run | Time (UTC) | After the open's read | After the run before |
|---|---|---|---|
| the open's read | 20:23:39.873 | 0 s | |
| first tick | 20:23:42.221 | 2.3 s | 2.3 s |
| minute read | 20:24:42.235 | 62.4 s | 60.0 s |
| minute read | 20:25:42.248 | 122.4 s | 60.0 s |

No run happened between those, and none in the 25 seconds after the last.
A read on every 5-second tick, as 0.2.2 did, would have given about 30
runs in the same window.

Verdict: pass. The runs follow the expected pattern: the open's read, one
read on the first tick, none on later ticks until 60 seconds after that
second read, then one a minute.

Evidence: `step5-runs.txt`, `step5-pane-screen.txt`.
