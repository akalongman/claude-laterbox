# Laterbox 0.3.0: native Windows in Claude Code

Status: draft for the owner's review. Date: 2026-10-16. Amends
`2026-10-15-laterbox-0.2.0-design.md`; what this document does not change
stays as that document, the code at `b9edd6b` and its tests define it.

## Intent

Laterbox is for people who park ideas while they work and come back to them
later. 0.3.0 makes it work for a regular Windows user inside Claude Code:
someone who installed Claude Code with the normal Windows installer, works
in PowerShell or Windows Terminal, and has never heard of Git Bash.

Worked example, used throughout. Nino Beridze runs Windows 11 and works in
`C:\Users\Nino Beridze\work\billing` (the space in her profile folder is
deliberate: it is where Windows plugin paths break). She installed laterbox
from the plugin directory. Mid-turn she types
`/later check the export totals` and keeps working. At the end of the day
she types `/later`, looks through the pane, ticks one note off and starts
another. Once she asks Claude "what's parked?".

Today (0.2.2) every one of those steps fails for her: the module starts
`later.sh` directly, and Windows cannot start a `.sh` file; the skill tells
the model to run a bash command, and on Windows the model reaches for
PowerShell first. After 0.3.0 all of them work, with nothing for her to
install or configure.

Success looks like this: on the owner's Windows 11 machine, Nino's day above
works end to end, quickly, with no console window ever appearing, and every
failure says in one plain line what went wrong and what to do.

## Baseline

The repository at `b9edd6b` (0.2.2 plus the directory icon):

- `scripts/later.sh`, the engine, already runs under Git Bash: the Windows
  CI job runs its whole test suite there, and the 2000-note `rows` timing.
- `hooks/hooks.json`: the `SessionStart` command hook with `"shell": "bash"`
  runs `bash "${CLAUDE_PLUGIN_ROOT}/scripts/later.sh" session-start`. On
  Windows Claude Code runs it through the Git Bash it finds itself.
- `hooks/register.tsx`, the hooks module: `/later <note>`, the pane (bare
  `/later`), each through `$.process.run([<root>/scripts/later.sh, ...args])`
  with a 10-second limit. The pane refreshes every 5 seconds
  (`REFRESH_MS`), each refresh one `later.sh rows` run. A failed park prints
  `later: could not park the note (<reason>); typed: <typed>`.
- `skills/notes/SKILL.md`: the model runs `later.sh list|add|done|drop`
  through the Bash tool, quoting the note for bash (`'\''`).
- The terminal link step in `later.sh` returns at once on anything but
  Linux and macOS.

Two facts checked on 2026-10-16 that shape this design:

- Installing laterbox needs git. Every one of the 315 plugins in Anthropic's
  official marketplace comes from a git source (164 `.git` URLs, 98
  `git-subdir`, 53 paths inside the marketplace's own git clone), and the
  `akalongman` marketplace is a GitHub repository. On Windows the git that
  Claude Code's own troubleshooting points to is Git for Windows, which
  ships `bin\bash.exe`. So for a user who installed the plugin, bash is
  almost always on the disk already; 0.2.2 just never looks for it.
- The module API (Claude Code 2.1.296 types) has `$.env.get(<literal
  name>)`, `$.fs.read|write|list|exists|stat|ancestors`, `$.process.run`
  with `{ cwd, env, stdin, timeoutMs }` and no option to hide a window, and
  `$.tool.register` for a tool named `mcp__<plugin>__<name>`, answered by a
  `tool.call` hook. It has no platform field. `$.fs` cannot append, rename,
  delete, create exclusively or lock.

## Goals, non-goals, anti-goals

Goals:

1. `/later <note>`, the pane, the skill and the session-start line work on
   native Windows in the Claude Code CLI.
2. The module finds Git for Windows' bash by itself.
3. The pane stops starting the engine when the queue has not changed, on
   every platform.
4. The skill reaches the engine without a shell command.

Non-goals:

- The terminal command `later` on native Windows (no `later.cmd`, no shims,
  no PATH work). The README keeps saying it is not available there.
- A second engine in PowerShell or TypeScript.
- Claude Code without Git for Windows' bash (MinGit, Git without bash):
  laterbox says so in one line instead of working.
- The desktop app, IDE extensions and SDK hosts on Windows.
- Any change to the queue format, the commands users type, the rewrite, or
  Linux and macOS behaviour beyond goals 3 and 4 and the text transport of
  1.8.

Anti-goals (the owner's four; each is a failure even if everything else
works):

1. **Slowness**: parking or opening the pane feels slow.
2. **Flashing windows**: a console window appears, once or every few
   seconds.
3. **Setup steps**: the user must install, configure or edit anything
   beyond installing the plugin.
4. **Silent failure**: something breaks and the user sees nothing, or only
   a technical error.

## Decisions taken with the owner

1. **Audience**: a regular Windows user parking ideas while working in
   Claude Code.
2. **Scope**: Claude Code entry points only. The terminal command stays
   Linux and macOS only.
3. **One engine.** Windows runs the same `later.sh` through Git for
   Windows' bash. A TypeScript engine on `$.fs` was rejected because `$.fs`
   cannot lock: two sessions parking at once could each read five notes and
   write back six, losing one note. A PowerShell engine was rejected as a
   second engine to keep in step, with a start time of about half a second
   per call in Windows PowerShell 5.1.
4. **Nothing to set up.** The plugin does not ask for git; it finds the
   bash that the plugin's own install brought. Only when no bash exists does
   it ask the user to install Git for Windows.
5. **The four anti-goals above** are release criteria, measured on the
   owner's Windows 11 machine (R8).

## Requirements

### R1. Finding bash on Windows

1.1 The module treats the host as Windows when the variable `OS` is
`Windows_NT`, which Windows sets for every process. This also covers a
plugin root on a network share (a roaming profile's
`\\server\profiles\...`), which a drive-letter test would miss. Elsewhere
nothing in this section applies and the engine runs as today.

1.2 On Windows the module runs the engine as
`[<bash>, <root>/scripts/later.sh, ...args]`, the script path in
forward-slash form, never the script alone as argv[0].

1.3 `<bash>` is the first candidate that passes the checks below. Every
step reads variables and asks `$.fs.exists`; none starts a process.

1. `SHELL`. Claude Code on Windows sets it, at startup, to the Git Bash it
   resolved for its own hooks (observed in 2.1.301, not documented).
2. `CLAUDE_CODE_GIT_BASH_PATH`, Claude Code's documented override.
3. `Git\bin\bash.exe` under each of `ProgramFiles`, `ProgramW6432` and
   `ProgramFiles(x86)`, duplicates dropped, in that order.
4. `Programs\Git\bin\bash.exe` under `LOCALAPPDATA` (Git for Windows'
   per-user install).
5. For each folder on `PATH` that holds `git.exe`, in `PATH` order,
   `bin\bash.exe` in that folder's parent (`C:\Program Files\Git\cmd`
   gives `C:\Program Files\Git\bin\bash.exe`). This is the rule Claude
   Code applies to the `git` it finds on `PATH`.

A candidate passes when it is non-empty, its file name is `bash.exe`,
`sh.exe`, `bash` or `sh` (Claude Code's own rule for its override, so the
module and the hooks never pick different files from the same value), it
exists, and it is not under `System32`, `SysWOW64` or `WindowsApps`, which
hold WSL's `bash.exe`, a launcher for Linux. A bare `bash` is never used.

1.4 The search runs once per session. `session.start` starts it and does
not wait for it before calling `next(e)`, so a slow file system never
delays the session's start; a `/later`, pane or tool call that arrives
before it finished waits for its result. The result (a path, or not
found) is kept for the session. There is no second search in the same
session: a found bash that later fails to start is reported as 4.2 says,
and the next session searches again.

1.5 The file started is Git's launcher, `bin\bash.exe`, the one Claude
Code runs its own hooks with; step 1 of 1.3 makes it the very same file
whenever Claude Code found one. The launcher sets `MSYSTEM`, puts Git's
`mingw64\bin` and `usr\bin` before the inherited `PATH`, and sets `HOME`
when it is unset, before it starts `usr\bin\bash.exe`. So the engine's
tools (`sed`, `tr`, `date`, `find`, `sort`) resolve to Git's, and the
module's runs see the same `HOME`, so the same state folder, as the
session-start hook. `usr\bin\bash.exe` is started directly only if R8.3
shows the launcher breaking R5; the module then sets `MSYSTEM`, `PATH`
and `HOME` itself, as the launcher would. A candidate that names
`usr\bin\bash.exe` (an override can) is used as given.

1.6 The variables read (`OS`, `SHELL`, `CLAUDE_CODE_GIT_BASH_PATH`,
`ProgramFiles`, `ProgramW6432`, `ProgramFiles(x86)`, `LOCALAPPDATA`,
`PATH`) are named as string literals, as `$.env.get` requires, and the
README lists them (R7).

1.7 Under Git Bash, whatever started it, the engine makes sure Git's
`/usr/bin` comes before Windows' system folders on `PATH`, so Windows'
own `find.exe` and `sort.exe` in `System32` never stand in for Git's. It
recognises Git Bash from `OSTYPE` (bash sets it to `msys`) or `MSYSTEM`,
without starting a process.

1.8 User text reaches the engine through standard input, never as an
argument, on every platform: the note of `add` (from `/later`, the pane
and the tool), and the expected text of every guarded `done` or `drop`
(the pane's close and drop, which pass it today as an argument, and the
tool of R3). Reason: Git for Windows' runtime rewrites the command line of
a process a native Windows program starts, before bash sees it. Any
argument that does not begin with a quote and begins with `@` is replaced
by that file's contents, and any word holding `?`, `*`, `[`, `"`, `'`,
`(`, `)`, `{`, `}` or beginning with `~` is globbed; a word without
spaces reaches it unquoted. Worked example: Nino types `/later @README.md`
in a project that has a README; passed as an argument, the stored note
would become the README's contents. And a note `fix (the) export` closed
from the pane would fail its guard and report a change that never
happened. The engine gains a way to read those texts from standard input.
The terminal command keeps taking its note as arguments, which bash hands
to bash unchanged.

### R2. A pane that starts no process while nothing changes

2.1 The engine's `rows` header becomes `queue\t<label>\t<path>`, `<path>`
being the queue file's absolute path in a form the module's `$.fs.stat`
accepts: unchanged on Linux and macOS, the Windows form with forward
slashes under Git Bash (`C:/Users/Nino Beridze/work/billing/LATER.local.md`,
not `/c/Users/...`). The path is printed whether or not the file exists.
Under Git Bash the engine takes that form from Git Bash itself (`pwd -W`
in the queue's folder, or `cygpath -m`), not by rewriting the string, so
every path Git Bash can name converts: other drives, network shares, and
MSYS folders such as `/tmp`. The conversion keeps the engine within the
process budget that the Linux CI job enforces with `strace`.

2.2 On each 5-second tick the pane reads the session's working directory
(`$.session.cwd()`) and looks at `<path>`: `$.fs.exists` first, then
`$.fs.stat` when it exists. None of this starts a process. It runs `rows`
only:

- when the working directory differs from the one its last `rows` ran in
  (a `cd` during the session can move the queue to another project);
- when the file's modification time or size differs from what it saw;
- when the file appeared or disappeared (`exists` turned true or false);
- after the pane's own writes (its add, done and drop);
- after the queue file setting changed;
- and in any case at least once every 60 seconds (filesystems with
  one-second timestamps can hide a same-size change, such as `[ ]`
  becoming `[x]`, made within the second of the last read).

The baseline it compares against is taken by a look made before the
`rows` it runs, never after: a write that lands between the two then costs
one extra `rows`, instead of hiding until the 60-second read.

2.3 When `$.fs.exists` rejects (the module's file layer refuses network
locations untouched, and `exists` rejects for nothing else) or `$.fs.stat`
rejects for a file that exists (an access refusal), the gate cannot see
that queue. The pane then runs `rows` on every tick, as 0.2.2 does, and
5.3 does not apply to that queue.

2.4 Before any pane action on a note (done, drop, putting it into the
prompt), the pane compares the working directory with the one its listing
came from. When they differ it refreshes and does not act, so a listing of
project A never acts on project B.

2.5 This applies on every platform. On Linux it saves a bash start every
5 seconds as well.

Worked example: Nino leaves the pane open for ten minutes while she codes.
Before: 120 `rows` runs. After: about 10 (the one-minute safety reads), plus
one each time a note is parked from another session.

### R3. The skill reaches the engine through a tool

3.1 At `session.start` the module registers one tool, `queue`
(`mcp__laterbox__queue`), not deferred, with input
`{ action: "list" }`, `{ action: "add", note: string }` or
`{ action: "done" | "drop", number: number, text: string }`. `done` and
`drop` act on one note, named by its number and its text in the listing the
model just took. Anything else is refused with a one-line reason and runs
nothing.

3.2 The tool runs the engine as R1 says: `list`; `add` with the note on
standard input (1.8); `done` or `drop` guarded by the note's text through
the engine's existing `--if`, that text on standard input. When the queue
changed since the listing and the note at that number is no longer the one
named, the engine refuses and changes nothing. Worked example: the listing
shows A, B and C; another session closes A; `drop` of number 2 with text
"B" is refused instead of dropping C. The tool returns the engine's output,
or a failure line of R4. It runs in the session's working directory, which
is `$.process.run`'s default and what `/later` relies on today, so the
engine finds the same queue.

3.3 `SKILL.md` names the tool for every operation: one note per call, a
fresh listing before each `done` or `drop`, and on a refusal a new listing
and a question to the user. It keeps every rule it has now: asking when a
note is ambiguous, never starting a note without the user's confirmation,
never editing the file by hand, the note as data. Its `allowed-tools` names
the tool instead of the four Bash commands.

3.4 Gate before 3.3 ships: a live check on Linux and on the Windows 11
machine that, in a session with the plugin loaded, "what's parked?" makes
the model call the tool with no permission dialog and no tool-search step.
The skill's `allowed-tools` line and the tool's `isDeferred: false` are
meant to make both certain; the check confirms them. If both pass, the skill names only the tool. If
either fails, the skill
adds a fallback used only when the tool is not available in the session:
the Bash commands with the engine's path double-quoted (Nino's plugin path
has a space) and `done` and `drop` guarded with `--if`, with matching
`allowed-tools` rules. That fallback ships only after it passes list, add,
done and drop live on the platform that failed, with a plugin path that
contains a space.

3.5 The module takes no permission decision for its tool: it answers no
`tool.check` event. What lets the tool run without a dialog is the skill's
`allowed-tools` line (3.3), the same mechanism that lets the skill's Bash
commands run today; it holds while the skill is active, and a call made
outside the skill gets Claude Code's ordinary dialog. Worked example: Nino
asks "what's parked?", the skill loads, and the tool runs without a
dialog; a user who wrote a deny rule for it stays denied. An answer that
turned Claude Code's `ask` into `allow` was in this design until
2026-11-05 and was dropped: the directory's scan holds a mod that takes a
permission decision for a reviewer, laterbox is already held for content
policy review, and a second hold category risks a rejection for one
spared dialog. If the gate of 3.4 fails without it, the answer may come
back as a deliberate decision, with a README sentence (R7) explaining it.
The README says what the module does not do (R7).

### R4. Every failure says what happened and what to do

4.1 No bash found (Windows): at session start the module shows, once per
session, `laterbox: Git for Windows' bash was not found. Install Git for
Windows (https://git-scm.com/download/win) and restart Claude Code.` After
that, `/later <note>` prints the existing failure template with that reason
(the typed text stays on screen), the pane shows the line in place of the
notes, and the tool returns it.

4.2 Any other failure to run the engine is reported as one of these kinds,
each with what to do; the raw message (error code, exit code, standard
error) goes to the debug log only, and `/later` keeps the typed text on
screen as today:

- the bash found at session start is gone: it was moved or removed;
  restart Claude Code to search again;
- the engine script is missing (bash starts, the script does not): the
  plugin's files are incomplete; reinstall laterbox;
- Windows refused to start bash (access denied, blocked by security
  software): name the path; check the security software or ask an
  administrator;
- no answer within the 10-second limit: the queue did not answer in time;
  try again;
- anything else: the engine could not run; start Claude Code with
  `--debug` for details.

The engine's own messages (a read-only queue, an empty queue) are already
plain and pass through unchanged.

4.3 A command hook that cannot run because Claude Code finds no Git Bash
is Claude Code's to report; the module's line in 4.1 is what tells the user
what to do.

### R5. Speed and no console windows

On the owner's Windows 11 machine, with a default Git for Windows install,
Microsoft Defender on, a profile path with a space, and three queues:
empty, 20 open notes, and 200 open notes in a 2000-line file (the shape of
the CI timing case), notes of about 80 characters. Each measurement is a
warm median of ten after one unmeasured run; the first run after the
machine boots is recorded separately and reported, not bounded.

5.1 With `laterbox.rewrite` set to `off`, the time from Enter on
`/later <note>` to the confirmation row has a median under 1 second, and no
run over 2 seconds, for each queue. With the default `haiku`, the model
call dominates on every platform; it is reported, not bounded.

5.2 Opening the pane shows the notes within 1 second (median), for each
queue.

5.3 An open pane on an unchanged queue starts no engine process for 60
seconds except the safety read of 2.2.

5.4 No console window appears at any point: session start, `/later`, the
pane's open, refresh and actions, the tool. This is a release blocker. If
`$.process.run` cannot start bash without a window, the work stops and the
owner decides the next step.

### R6. Linux and macOS

Only 1.8 (user text on standard input), R2 and R3 change behaviour there.
The engine's other output, the terminal command, the link step and the
session-start hook are unchanged.

7.1 The Platforms table's Windows row says: works in the Claude Code CLI

### R8. Tests, CI and live verification

8.1 Module tests (`claude plugin test`) cover: the Windows test of 1.1;
every step and check of 1.3, including the file-name rule, the refused
folders and the not-found result; that no call site (`/later`'s park, the
pane's add, close and drop, the tool) puts user text in the argument
vector, and that each sends it on standard input (1.8); the refresh
decision of 2.2 (changed, unchanged, appeared, disappeared, own write,
setting changed, working directory changed, 60-second safety read, look
before read), the polling fallback of 2.3 and the action check of 2.4; the
tool's input checks and its single-note guarded form; the failure kinds
of 4.2. The search and the refresh decision
are pure functions over injected lookups, so they are tested without a
Windows host. Each test is seen to fail against unchanged code first; for
a function that does not exist yet, that failure is the missing function
or the old behaviour, not a stub written to fail.

8.2 Engine tests, on every CI platform, cover: the new `rows` header, and
on the Windows job the forward-slash Windows form of the path; reading the
note and the guard text from standard input, each stored or matched byte
for byte for `@README.md` (with that file present), `*.md`, `"quoted"`,
`it's`, `C:\x\`, a leading `-`, and Georgian text; and, on the Windows job,
`/usr/bin` leading `PATH` (1.7). CI cannot reproduce Git for Windows'
command-line rewriting, because its bash is started by bash, so 8.3 checks
it live.

8.3 Live verification on the owner's Windows 11 machine before the tag,
with the working tree brought over without pushing `main` (a shared folder
or a git bundle; see R9): Nino's day of the Intent; R5's measurements;
which step of 1.3 found bash, and that `SHELL` names the file Claude
Code's hooks use; that the launcher of 1.5 meets R5, or why
`usr\bin\bash.exe` replaced it; the text round trip of 8.2 through
`/later`, the pane's close and the tool; that the hook and the module use
the same `HOME` and state folder, also with `CLAUDE_CODE_GIT_BASH_PATH`
naming `usr\bin\bash.exe`; a `cd` to another project through Claude's
shell, then `/later`, the pane and the tool, each reaching the queue the
engine finds from that folder (if the shell's `cd` does not move the
session's directory, 2.2's first bullet is moot but harmless); the no-bash
line of 4.1 with Git's folder renamed away; the tool gate of 3.4; the
session-start line through the `SessionStart` hook, which 0.2.2 never ran
on native Windows. The session-start line is one of goal 1's entry
points, so a failure there is fixed in this release, not only observed.
The results are written to a dated file under `docs/superpowers/` and
committed with the release.

### R9. Release

Version 0.3.0, signed tag `v0.3.0`, CI green on all three runners. The
directory review of 0.2.2 tracks `main` and locks the branch while it runs,
and every push to `main` reaches the directory within minutes, so `main` is
not pushed while that review runs. When 0.3.0 is ready before the review
ends, the owner decides between waiting and pushing a separate branch with
a pull request to `main`: the workflow runs on pushes to `main` and on pull
requests to `main`, so a branch push alone runs no CI. After the review
ends the owner switches the directory's tracked branch to `release`; then
`main` is pushed, CI passes, the tag is pushed, and `release` is moved
forward to `v0.3.0`.

## Designer's calls for the owner to check

1. Windows is detected from the variable `OS` (1.1), which also covers a
   plugin root on a network share.
2. The search order of 1.3: Claude Code's own choice (`SHELL`) first, then
   its override, the standard install folders, and a scan of `PATH` for
   `git.exe`; no process, once per session, no retry (1.4).

   call site, not only Windows, so there is one path to test (1.8).
5. The refresh gate applies on every platform, with the working-directory
   check, a look before each read, a read at least once a minute, and
   polling where a queue cannot be seen (R2).
6. The skill moves to the tool on every platform, one note per call,
   guarded by its text; a Bash fallback is added only if the gate fails,
   and is used only when the tool is missing (R3).
7. The module takes no permission decision for its tool; the skill's
   `allowed-tools` line pre-approves it while the skill is active (3.5,
   decided with the owner on 2026-11-05).
8. The `rows` header carries the queue path, an internal format change
   between two files that always ship together (2.1).
9. The engine converts the queue path with Git Bash's own tools (2.1).
10. The five failure kinds of 4.2 and their remedies.
11. The 1-second and 2-second numbers of R5, and its three queues.
12. Raising the Claude Code version floor is acceptable (7.3).

## Known risks

- The module API is early access: `$.process`, `$.env`, `$.fs`,
  `$.session.cwd` and `$.tool` can change between releases. R8.3 is repeated when the version floor moves.
- `SHELL` as Claude Code's choice of Git Bash is observed, not documented;
  if a release stops setting it, 1.3's other steps still find bash.
- In the CLI a console program started by Claude Code shares its console,
  so no window is expected; R5.4 still checks it, because a host without a
  console would show one, and `$.process.run` has no option to hide it.
- Git for Windows' command-line rewriting is avoided by 1.8, not tested in
  CI; only R8.3 sees it.
- The directory may raise new holds for the variables the module reads
  and for its working-directory and file reads; the README (R7) answers
  them for the reviewer.
- A skill's `allowed-tools` line may not pre-approve a tool a mod
  registers; the gate of 3.4 shows it, and 3.5 names the answer.
- A registered tool may still show a tool-search step; 3.4 has the
  fallback.
- A queue on a network share polls as in 0.2.2 (2.3).
- A user whose git has no bash (MinGit) gets the line of 4.1 and must
  install Git for Windows.
- Native Windows and WSL parking into one project still do not share a
  lock; the README's WSL row already says so.
