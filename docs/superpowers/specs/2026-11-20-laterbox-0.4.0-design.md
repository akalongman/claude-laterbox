# Laterbox 0.4.0: a queue tool that spends little context

Status: approved by the owner on 2026-11-20. Date: 2026-11-20. Amends
`2026-10-16-laterbox-0.3.0-design.md`; what this document does not change
stays as that document, the code at `04b00f3` (0.3.2) and its tests define
it. Section numbers of that document are written "0.3.0 R3.2"; bare
numbers are this document's.

## Intent

A model that works the queue through the tool `mcp__laterbox__queue` pays
for every character the tool takes and returns. Today that price grows
with the length of the notes, and the notes are long. 0.4.0 makes the
price depend on how many notes there are and on which ones the model
reads, not on how long they are.

Worked example, used throughout. Nino Beridze's `billing` queue holds 40
open notes that sessions parked for her, about 500 characters each. She
asks: "do the note about the export totals, then drop the two about the
old importer."

Today (0.3.2), following the skill: a listing, the work, a fresh listing,
`done` with the note's 500 characters in the call and again in the result,
a fresh listing, `drop`, a fresh listing, `drop`. Four listings of about
20,000 characters each and three notes sent twice: about 83,000
characters.

After 0.4.0: one listing with each note clipped to 100 characters (under
5,000 characters), one `show` of the note she wants done (about 520), one
`done` and one `drop` naming notes by an 8-character id, and three result
lines: about 6,000 characters.

Both totals are arithmetic on the example, not a measurement; 9.3 has the
measurement.

Success looks like this: Nino's request above costs under a tenth of what
it costs on 0.3.2, a close never needs a second listing, and a close can
no longer fail because the model miscopied a note's text.

## Baseline

The repository at `04b00f3` (0.3.2):

- `hooks/tool.ts`: the tool takes `{ action: "list" }`,
  `{ action: "add", note }` and
  `{ action: "done" | "drop", number, text }`. A close names one note by
  its number and its exact text from a listing, and the engine's `--if`
  refuses it when the note at that number no longer has that text.
- `hooks/register.tsx`: the `tool.call` hook returns the engine's output
  as the result. `list` returns every open note whole; `add` answers
  `later: parked -> <note>` and a close `later: done -> <text>`, each with
  the whole text.
- `skills/notes/SKILL.md`: one note per call, and a fresh listing before
  each `done` or `drop`, because numbers shift when a note closes.
- `scripts/later.sh`: `rows` prints one line per open note for programs
  (position, age, text); `done|drop --if` takes exactly one note. The pane
  names a note by its text and its occurrence among open notes with the
  same text (`noteKey` in `hooks/register.tsx`).
- The tool's description, which every session carries, is 862 characters.

So one note's text enters the conversation on the `add` call, in the `add`
result, in every listing, on the close call and in the close result.

Facts checked on 2026-11-20 that shape this design:

- Long notes are the normal case. Over the 36 queue files on the owner's
  machine: 461 open notes, median 501 characters, 391 of them (85%) over
  300, the longest 1,917. The largest queue has 103 open notes and 62,510
  characters per listing. Lengths were counted with a parser that follows
  the engine's line rules, stamp excluded.
- The listing is the cost, not the close: in that largest queue one
  listing is 62,510 characters, and closing one median note by its text
  about 1,000.
- A cap on the note `add` accepts would not fix it: the 461 notes exist,
  and a cap of 300 would refuse most notes sessions write today.
- The engine's process rule (0.2.0 R5.6, the suite's "process budget"
  case) allows no process per note, which rules out hashing each note with
  a program inside `later.sh`. The module's environment has
  `crypto.subtle.digest`, which answers asynchronously and whose presence
  at the 2.1.296 floor was not checked; the id needs neither, since a
  32-bit hash is a few lines of arithmetic.
- The marketplace lists this repository with no pinned commit or branch
  (`akalongman/claude-plugins`, `.claude-plugin/marketplace.json`), so a
  version bump on `main` is the release.

## Goals, non-goals, anti-goals

Goals:

1. A listing through the tool costs at most about 125 characters per open
   note, whatever the notes' length.
2. A note's whole text enters the conversation only when the model asks
   for that note.
3. A close names notes by a short id, never by text, and several notes
   close in one call.
4. One listing serves a whole piece of work: no fresh listing before a
   close.
5. The tool accepts no note over 2,000 characters.

Non-goals:

- A limit on note length anywhere but the tool's `add`: `/later`, the
  pane's add and the terminal command take what they take today.
- Any change to the queue file's format, to the terminal command's output,
  to the pane, to the session-start line, or to what bare `/later` prints
  in a session without panes.
- Archiving or pruning ticked lines. They never reach a listing, so they
  cost no context; it is a separate piece of work.
- Ids in the terminal command or the pane.

Anti-goals (each is a failure even if everything else works):

1. **A weaker lock-time guard**: the engine closing a note whose text it
   did not compare byte for byte under the lock.
2. **A wrong note closed** because an id was miscopied or stale. R1.5
   states exactly how far this is excluded.
3. **A dead end**: a note the model can list but cannot read whole.
4. **A longer tool description**: every session pays for it.

## Approaches

Three ways to name a note without its text were considered.

1. **The id is computed in the module (chosen).** The tool reads the
   engine's `rows`, computes each note's id, clips the listing, and turns
   an id back into the note's number and whole text before it asks the
   engine to close. The engine still compares whole texts under the lock.
   The terminal command and the pane do not change. Cost: one `rows` run
   before a close, and one addition to the engine so several guarded
   closes are one run.
2. **The id is computed in the engine.** `later.sh list` would print ids
   and `done <id>` would work from the terminal: one identity everywhere.
   Rejected: hashing in bash with no process per note, with the same
   result under bash 3.2, Git Bash and a byte locale, over 50,000
   characters for a large queue, puts the most fragile code in the file
   that must stay the most portable.
3. **No id: clip the listing and guard a close by the clipped text.**
   Rejected: notes written in a series share their first words, so the
   guard would not tell them apart, and 0.3.0 R1.8 already treats a guard
   by the first part of a text as a defect. The model would also still
   have to copy 100 characters exactly.

A fourth, an id stored in the queue file beside each note, was dropped
early: it changes the format of every existing queue and shows in every
hand edit.

The owner chose approach 1 on 2026-11-20.

## Decisions taken with the owner

Taken on 2026-11-20.

1. **Long notes stay.** They carry what a later session needs. They are
   made cheap to list, not forbidden.
2. **Approach 1**, with the engine addition for a close of several notes.
3. **A close names notes by id alone.** The number stays in the listing,
   so "drop note 3" still maps to a note, and leaves the call.
4. **The listing clips each note at 100 characters**, the width the
   session-start line already uses.
5. **`add` through the tool refuses a note over 2,000 characters.**
6. **The `{ number, text }` form of `done` and `drop` is removed**, not
   kept beside the new form: the tool and the skill ship together.
7. **The skill** takes one listing and closes by id, several notes per
   call.
8. **Ticked lines are out of scope.**
9. **The release goes through a branch `release-0.4.0` and a pull
   request** (R10), so macOS and Windows judge it before `main` moves.

## Requirements

### R1. Note ids

1.1 An id names one open note by its content: it is computed from the
note's text as `rows` prints it (the stamp is not part of it) and the
note's occurrence among the open notes with exactly that text, counted
from 1 in queue order. That is the pane's existing naming rule. The
note's number and age are not part of it.

1.2 An id is 8 lowercase hexadecimal characters: a 32-bit hash of 1.1's
two inputs. It is computed by a pure function in the module, with the same
result in every session and on every platform. The engine neither computes
nor stores ids, and the queue file does not change.

1.3 What follows from 1.1. Worked example: the queue holds A, B and C.
Closing A leaves the ids of B and C as they were, although their numbers
changed. Parking D changes no id. Editing B's text in the file gives B a
new id, and its old id names nothing. Of two notes with the same text, the
second takes the first's id when the first closes, which is harmless: the
two were the same note twice.

1.4 An id names nothing when no open note has it, and is ambiguous when
two open notes with different texts have it (a hash collision: for 100
open notes about 1 chance in 860,000, for 1,000 about 1 in 8,600). A call
that names such an id is refused whole, as R3 and R4 say. The listing
still shows both notes, and the pane and the terminal command can still
close them.

1.5 What the id guarantees, stated plainly. Between the module's own
reading of the queue and the engine's rewrite, the guard is today's: the
engine compares each note's whole text byte for byte while it holds the
queue's lock, so no writer that takes the lock can change a note between
the check and the rewrite. Between the model's listing and the module's
reading, the guard is the id: when the listed note was edited or closed
in between, the call is refused unless a different open note happens to
have the same id, about 1 chance in 4,300,000,000 for each open note.
That narrows the window to a negligible size; it does not close it, as
the text comparison of 0.3.2 did. A miscopied id is refused on the same
odds. A hand edit in an editor takes no lock, in this version as in
every earlier one.

### R2. The listing

2.1 `{ action: "list" }` runs the engine's `rows` once, and the module
writes the result:

```
billing: 40 parked
 1. [a41c9e07] Recheck the export totals for March against the ledger, the run of 2026-11-02 showed a difference... (12d)
 2. [07be33aa] Remove the old importer's retry table once the new importer has run for a week (3d)
```

The first line is the queue's label and the count of open notes; then one
line per open note in queue order: its number as the engine's `list`
writes it, its id in square brackets, its text, and its age in
parentheses. With no open note, or no queue file, the result is
`later: no parked notes`.

2.2 A text longer than 100 characters is cut to its first 97 and `...`,
the rule of the engine's own clipping. A character is a Unicode code
point, and the cut never splits one. A text of 100 characters or fewer
is written whole, so a line that does not end its text in `...` shows
the whole note.

2.3 The engine's `list` is unchanged and stays what the terminal command
and bare `/later` in a session without panes print. A `rows` run that
fails is reported as 0.3.0 R4 says. One difference follows from reading
`rows`: in a working directory the engine cannot resolve, the tool's
`list` now answers with the engine's refusal
(`later: cannot resolve the queue here`) where it answered
`later: no parked notes`.

### R3. Reading notes whole

3.1 `{ action: "show", ids: [...] }` returns each named note whole, one
line per note in queue order, in the listing's line format without the
cut. It runs `rows` once and nothing else.

3.2 When any id of the call names nothing or is ambiguous, the whole call
is refused with one line that names each such id, for example
`later: no open note [07be33aa]; list again`.

### R4. Closing by id

4.1 `{ action: "done" | "drop", ids: [...] }` closes the named notes. An
id given twice counts once.

4.2 The module runs `rows` and resolves every id. When any names nothing
or is ambiguous, the call is refused as 3.2 says, with `nothing changed`
in the line, and no closing run starts.

4.3 Otherwise one engine run closes all of them. Each note is named by
its number in that `rows` reading and its whole text. Holding the queue's
lock, the engine compares every named note with its text before it
changes anything; when any differs or is missing, it refuses with today's
line (`later: note <n> changed since it was listed; nothing changed`) and
the queue file stays byte for byte as it was. When all match, one rewrite
closes them all. Worked example: the queue holds A, B, C and D, and the
call drops B and D. The module reads the queue and sends "2 is B, 4 is
D". If another session closed A in between, note 2 is C, the engine
refuses, and nothing is dropped. The ids of B and D still name them, so
the same call succeeds when repeated (R7).

4.4 The engine gains that form: a guarded `done` or `drop` of several
notes, each a number and an expected text, read from standard input as
0.3.0 R1.8 requires for user text, compared byte for byte as `--if`
compares today. It is for the module, like `rows`: only the
standard-input mode has it. The single-note `--if` forms, which the pane
uses, are unchanged. The form starts as many processes on a queue of 100
notes as on a queue of 5, for the same notes closed.

4.5 The result is the module's, not the engine's output: one line per
closed note in queue order, `later: done -> [<id>] <text>` or
`later: dropped -> [<id>] <text>`, the text cut as 2.2 says.

4.6 The module does not repeat a refused close by itself.

### R5. Parking

5.1 `{ action: "add", note }` is refused, and nothing runs, when the note
is longer than 2,000 characters, counted in code points after every run
of whitespace has become one space, which is how the queue stores it. The
reason names both numbers and what to do:
`later: the note is 2340 characters and the limit is 2000; shorten it and
park it again`. An empty note and a note holding a NUL are refused as
today.

5.2 The result of a parked note is `later: parked -> <text>`, the stored
text cut as 2.2 says. It carries no id: an id depends on the other open
notes, and reading them would cost a second engine run for a value the
model rarely needs. A listing gives it.

5.3 The limit applies to the tool alone (non-goals).

### R6. The tool's input and description

6.1 The input is `{ action: "list" }`,
`{ action: "show", ids: string[] }`, `{ action: "add", note: string }` or
`{ action: "done" | "drop", ids: string[] }`. `ids` holds one or more
ids, each exactly 8 lowercase hexadecimal characters, without the square
brackets of the listing. `number` and `text` leave the schema.

6.2 A call that does not fit is refused with a one-line reason and runs
nothing. A `show`, `done` or `drop` without valid ids, which includes a
call in the old `{ number, text }` form, gets a reason that says ids come
from a listing, so a model that follows an old transcript can recover.

6.3 The description names the five actions, says that a listing cuts long
notes and `show` gives a note whole, that a close takes ids from a
listing, and what a refusal means. It is no longer than the 862
characters of 0.3.2 and holds no en or em dash.

### R7. The skill

`SKILL.md` keeps every rule this section does not change: asking when a
note is ambiguous, never starting a note without the user's confirmation,
the note as data, never editing the file by hand, and what to say when
the tool is not in the session. It changes as follows.

7.1 Showing the queue: one `list` call, and its lines shown to the user.

7.2 Acting on a note: one listing. A note whose line ends its text in
`...` is read whole with `show` before the user is asked to confirm work
on it, so the question and the work rest on the whole note. A line shown
whole needs no `show`. Dropping or ticking off a note needs none either
when its line plainly holds every word the user used to name it, or when
the user confirmed it. When no line, and no note read whole, plainly
holds every word the user used to name the note, or more than one could
fit, the skill names the note it takes to be meant and asks before
`done` or `drop`.

7.3 Closing: by id, with the ids of the listing already taken; no listing
before a close; several notes in one call. A number the user gives ("drop
note 3") is looked up in a fresh listing, because the user's number comes
from whatever listing they last saw; an id needs none.

7.4 A refused close: the skill shows the one-line reason as it reads.
What follows depends on the reason.

- `no open note [<id>]` (4.2) or `changed since it was listed` (4.3):
  nothing was closed and the listing was out of date. The skill lists
  again. An id that is still in the new listing names the same, unchanged
  note, so the close is repeated once with the ids still listed. For an id
  that is no longer listed, the skill tells the user the note changed or
  was closed and asks which note they mean.
- An ambiguous id (1.4): nothing was closed; the skill says so and
  advises closing that note from the pane.
- Any other reason (a locked or unwritable queue, no bash, no answer in
  time): the rule of 0.3.2 stays. The skill asks the user how to go on
  and does not repeat the close. After "did not answer within 10 seconds"
  the close may still have happened, since the engine can finish after
  the module stops waiting, so the skill does not say that nothing was
  closed; a listing shows what is open.

7.5 Parking: the rule of one self-contained line stays; the skill adds
that the tool refuses a note over 2,000 characters.

### R8. README

"What it runs" describes the tool as it now is: the five actions; that
`list`, `show` and a close each read the queue with `rows`; that a close
names notes by an id the module computes from each note's text, and that
the engine still compares whole texts before it changes the file; the
2,000-character limit; and R1.5's statement of what an id guarantees.
"Asking in words" needs no new claim. The Claude Code version floor stays
at 2.1.296: no new API is used.

### R9. Tests and live verification

9.1 Module tests cover: the id function (same input, same id; a changed
text, occurrence or single character gives another id; the format of
1.2; no two equal ids among 2,000 generated notes of realistic length);
the cut of 2.2 at 100 and 101 characters, with Georgian text and with a
character outside the basic plane at the cut; the listing, `show`, close
and park results line for line; every refusal of R3, R4, R5 and R6,
each with the engine runs it must not start; a close of several notes
as one closing run with every number and whole text on standard input and
none in the arguments; an id given twice; an ambiguous id; the old
`{ number, text }` form; the description's length and content. Each test
is seen to fail against unchanged code first.

9.2 Engine tests, on every CI platform, cover the form of 4.4: every text
matching closes all in one rewrite, for `done` and for `drop`; one text
differing, or one number past the end, refuses and leaves the file byte
for byte unchanged; a text with a tab, with trailing spaces, with Georgian
letters, with `@README.md` and with `*.md`; a queue with CRLF line ends
and one with a byte-order mark; the same under `LC_ALL=C`; the process
budget of 4.4; that the single-note forms answer as before.

9.3 A module test measures the example: on a staged queue of 40 notes of
500 characters, the `list` result is under 5,100 characters, and a `done`
of two ids starts two engine runs and returns under 300 characters.

9.4 Live verification on Linux before the tag, with the working copy
loaded in one session and the installed copy turned off, as the 0.3.0
checks were run: "what is parked?" on a queue of 40 long notes gives one
call and cut lines; "do note N", for a note whose line is cut, makes the
model read that note whole before it asks to start; Nino's request
closes three notes with no second listing; a note closed from the terminal between the model's listing and
its close gives the refusal and the skill's answer of 7.4. The tool
input and result characters of Nino's request are read from the session
record for 0.3.2 and for 0.4.0 and written down. The results go to a
dated file under `docs/superpowers/`, committed with the release. If the
model still lists before a close, the skill's wording is fixed and the
check repeated.

### R10. Release

Version 0.4.0, since the tool's input changes, with the signed tag
`v0.4.0`. The marketplace serves `main` as it stands (Baseline), and CI
runs only on a push to `main` and on a pull request to `main`. So the
macOS and Windows runners, the only places bash 3.2 and Git Bash meet the
engine's new form, can judge the work before it is published only from a
pull request. The owner chose that route on 2026-11-20: the work is
committed on a branch `release-0.4.0`, as 0.3.0 was, and reaches `main`
through a pull request once CI is green there. The version bump is part
of that branch, so no install gets the new tool under the old version.
Pushing the branch, opening the pull request, moving `main` and pushing
the tag are each the owner's to order when the work is done; approving
this document does not order them.

## Designer's calls for the owner to check

1. The id is 8 hexadecimal characters, not the 6 named when the
   approaches were shown: two more characters per note buy odds of 1 in
   4.3 thousand million instead of 1 in 16 million, and make a collision
   inside one queue rare enough to refuse it instead of lengthening ids.
2. An ambiguous id is refused and left to the pane or the terminal (1.4),
   with no scheme to tell the two notes apart.
3. `show` and a close are all or nothing: one bad id refuses the call.
4. `add` returns no id (5.2).
5. The 2,000 characters are counted after whitespace is collapsed, in
   code points (5.1).
6. The module does not retry a close the engine refused; the skill lists
   again and repeats it once (4.6, 7.4). A retry in the module would hide
   the rare case where another note closed in the same moment, at the
   price of the module reading the engine's refusal apart from its other
   failures.
7. The tool's `list` in a directory the engine cannot resolve now reports
   that, instead of "no parked notes" (2.3).
8. The id sits in square brackets in the listing and is given without
   them in a call (2.1, 6.1).
9. Live verification is on Linux only; Windows is covered by the engine
   suite on the CI runner (9.2), since no Windows-specific path changes.
10. The skill's rules of 7.2: `show` before the confirmation question for
    every note whose line is cut, and a question naming the note taken to
    be meant before a `done` or `drop` whenever no line, and no note read
    whole, plainly holds every word the user used to name it, or more than
    one could fit.
11. Only the two out-of-date refusals are listed again and repeated; every
    other refusal keeps the 0.3.2 rule of asking the user, and a timeout
    is no longer described as "nothing was closed" (7.4).

## Known risks

- The model may keep listing before a close out of habit; 9.4 checks it
  and the skill's wording is the fix.
- A cut line can hide the part of a note that tells two notes apart; the
  skill asks for `show` then (7.2), and the id never depends on the cut.
- A close refused because another note closed in the same moment costs
  one more listing and a repeated call (designer's call 6).
- A transcript from 0.3.2 holds calls in the old form; they are refused
  with a reason that says what to do (6.2).
- Sessions started before the update keep the old tool and the old skill
  until they restart, as with every release.
- The module API is early access, as 0.3.0 says.
