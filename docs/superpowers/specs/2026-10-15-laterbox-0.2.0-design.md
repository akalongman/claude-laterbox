# Laterbox 0.2.0: the directory-ready release

Status: draft for the owner's review. Date: 2026-10-15.

## Intent

The plugin `later` (version 0.1.0 plus the unpushed fix commit `63d4208`)
parks follow-up notes in a per-project Markdown queue. It is published in the
public repository `akalongman/claude-plugins`, but only its author uses it.
This release makes it fit for strangers and for Anthropic's plugin directory:

- the directory's automated checks pass without a reviewer hold that the
  layout or the README could have avoided;
- a stranger's existing files are never mistaken for the queue;
- the plugin runs on Linux and on a stock Mac (no Homebrew tools);
- the README tells a stranger everything the plugin runs, sends and writes.

The release also lays the groundwork for native Windows, which ships in
0.3.0 and is out of scope here except where noted.

Success looks like this: the owner submits the plugin in the developer
portal after this release, and the portal's validation reports nothing that
this repository could have fixed.

## Baseline

The repository at `63d4208`:

- `.claude-plugin/marketplace.json`: marketplace `akalongman`, one entry
  `later` with source `./plugins/later`.
- `plugins/later/`: the plugin. `hooks/hooks.json` holds a `SessionStart`
  command hook (matcher `startup`) that runs
  `"${CLAUDE_PLUGIN_ROOT}/scripts/later.sh" session-start`, and names the hooks
  module `hooks/register.tsx`. `scripts/later.sh` is the engine,
  `scripts/later` the terminal front-end, `skills/notes/SKILL.md` the skill,
  `tests/later.test.sh` and `hooks/register.test.ts` the tests,
  `types/index.d.ts` the module's state contract, `tsconfig.json` the
  type-check configuration.
- `README.md` and `LICENSE` (MIT) at the root; the README covers the plugin.

Behaviour this document does not change stays as the baseline code and its
tests define it.

## Goals, non-goals, anti-goals

Goals:

1. Rename the plugin and move it to the root of its own repository.
2. Rename the queue file to a name only this plugin uses, and make it a
   setting.
3. Make the engine run on stock macOS tools and cheaply on Git Bash.
4. Prove the above in CI on Linux, macOS and Windows (Git Bash).
5. A README that passes the directory's checks and discloses everything.

Non-goals (0.3.0 or later):

- Native Windows entry points: the hooks module finding Git's `bash.exe`, a
  tool the module registers for the skill, and Windows terminal shims
  (`later.cmd`). The README keeps "Windows: not supported yet; WSL works".
- Per-project queue file names.
- Any change to the queue format, the pane, the rewrite, or the commands a
  user types.

Anti-goals (a failure even if everything else works):

- The plugin writes to a file it did not create, or treats a stranger's own
  Markdown checkboxes as parked notes.
- The plugin edits git ignore files, shell startup files or PATH.
- A note lands in a different file depending on whether it was parked from
  the terminal, from `/later`, from the pane or by the skill.
- macOS support that silently depends on Homebrew tools.

## Decisions taken with the owner

1. **Plugin name `laterbox`**, shown as "Laterbox". Known risk, accepted: an
   unrelated iOS app named "LaterBox" may draw the directory's "Name matches
   a known brand" hold. A hold is not a rejection.
2. **Repository.** The GitHub repository `akalongman/claude-plugins` is
   renamed to `akalongman/claude-laterbox` (a rename, not a new repository:
   it keeps the ruleset that protects `main`, GitHub redirects the old URL,
   and no history is rewritten). The plugin moves to the repository root.
   The marketplace keeps the name `akalongman` and lists one plugin whose
   source is `"./"`, the shape the plugin reference documents for a
   single-plugin repository. Reason: the directory holds a plugin in a
   subfolder whose hook runs a non-shell file (the TypeScript module), and
   its stated fix is the plugin at the root of its own repository.
3. **What users type does not change.** `/later <note>`, bare `/later`, the
   terminal command `later` with `all`, `done`, `drop`, `--` and `--help`,
   the `LATER_*` environment variables, and the state folder
   `~/.cache/later/` keep their names. Only names derived from the plugin
   name change: the skill becomes `laterbox:notes`, the settings appear as
   `laterbox.<key>`, the data folder becomes `laterbox-<marketplace>`.
4. **Queue file `LATER.local.md`** by default, named after the command, not
   the product, so a future product rename does not touch every project.
   Worked example of the problem it solves: a user, Dana, keeps her own
   `NOTES.local.md` with `- [ ] ask Sam about the deploy`. With the 0.1.0
   name, her first `/later rerun the flaky test` appends to her file, the
   session-start count includes her checkbox, and `d` in the pane rewrites
   her file. With `LATER.local.md` none of her files is touched.
5. **The queue file name is a setting**, one value per person for every
   project, not per project. Reason: the terminal command and `later all`
   cannot read a project's Claude Code settings, so a per-project name would
   let the terminal and the session write different files.
6. **Git is the user's choice.** The engine never writes `.gitignore`,
   `.git/info/exclude` or a global excludes file. The README explains how to
   keep the file private or commit it.
7. **No migration code in the plugin.** The public repository was created on
   2026-10-15 and had no clones, views or stars when checked that day, so the
   owner's machine is the only 0.1.0 install. A one-off script outside this
   repository migrates it (see R10).
8. **Stock macOS.** The engine runs with bash 3.2 and the BSD tools of a
   stock Mac, with no Homebrew GNU tools on PATH. CI proves it on GitHub's
   macOS runner with PATH limited to the system folders.
9. **Two releases.** 0.2.0 is this document. 0.3.0 adds the native Windows
   entry points, verified on a Windows 11 machine. The owner submits to the
   directory after 0.2.0.

## Requirements

### R1. Repository layout

The repository root becomes the plugin root:

```
.claude-plugin/plugin.json        name laterbox, version 0.2.0
.claude-plugin/marketplace.json   name akalongman, one entry: laterbox, source "./"
hooks/  scripts/  skills/notes/  tests/  types/  tsconfig.json
README.md  LICENSE  .gitattributes  .gitignore  .github/workflows/
docs/superpowers/specs/           this document
```

1. Files move with `git mv`, so history follows them.
2. `plugin.json`: `name` `laterbox`, `displayName` `Laterbox` (if the
   manifest schema accepts the field; `claude plugin validate --strict`
   decides), `version` `0.2.0`, `repository`
   `https://github.com/akalongman/claude-laterbox`, `license` `MIT`, and a
   `description` that names the queue file setting's default instead of
   `NOTES.local.md` wherever it names the file.
3. `marketplace.json`: unchanged apart from the entry's `name` (`laterbox`),
   its `source` (`"./"`) and its description, which matches `plugin.json`.
4. Every path that names `plugins/later` (README, `.gitignore`, the type
   declarations' ignore line, test scripts, the develop commands) is updated.
5. The directory's file rules hold: no file over 256 KiB, at most 512 files,
   no `.DS_Store`, no `export-ignore` or `export-subst` in any
   `.gitattributes`.
6. `claude plugin validate . --strict` passes at the root and reads the
   marketplace, the manifest and the module in one run.

### R2. Names derived from the plugin

1. The hooks module keeps registering the slash command `later`. The module
   API declares a registered command as `/<name>` for the session, with no
   plugin prefix, so the rename does not change what users type. The
   verification section checks this in a live session.
2. Every user-visible string that names a setting as `later.<key>` (for
   example the terminal link notices in `later.sh`, the README) names it as
   `laterbox.<key>`. Every mention of the skill `later:notes` becomes
   `laterbox:notes`. Output lines that begin `later:` keep that prefix,
   because it names the command.
3. The README names the data folder by its pattern,
   `~/.claude/plugins/data/laterbox-<marketplace>` (the base follows
   `CLAUDE_CONFIG_DIR` when set), not only the `akalongman` instance. An
   install from another marketplace, including the directory's own, gets
   another folder name.
4. The module's state namespace follows the plugin name: the `atom`
   declarations in `hooks/register.tsx`, the `PluginState` entry in
   `types/index.d.ts` and the `plugin` fields in `hooks/register.test.ts`
   name `laterbox`. The engine lets only a value's owner write it, so a module
   that keeps `later` after the rename has every `command.run` hook skipped:
   bare `/later` and the pane do nothing. With the manifest renamed and the
   namespace not, `claude plugin validate . --strict` reports four errors of
   the form "`$.state.set` refers to later.queue, which later owns" and
   `claude plugin test .` fails 55 of 85 tests. Both must pass after the
   change.

### R3. The queue file and the `file` setting

1. New `userConfig` field `file`: string, default `LATER.local.md`, title
   "Queue file", description saying it is one name for all projects and that
   renaming does not move existing queues.
2. The heading written when a queue is created stays
   `` # Parked notes (`/later`) ``.
3. **One resolution rule for every entry point** (session-start hook, hooks
   module, the skill's shell calls, the terminal command, `later all`):
   1. the value Claude Code hands this run, when the run is one Claude Code
      started for the plugin:
      - the module passes `CLAUDE_PLUGIN_OPTION_FILE`, with the value from
        its `options` (defaults filled in), to every engine run, added to
        the inherited environment;
      - the session-start hook reads `CLAUDE_PLUGIN_OPTION_FILE`, and treats
        its absence as the default, because Claude Code exports an option to
        hooks only once the user has set it (observed on Claude Code
        2.1.296). So clearing the setting returns every entry point to the
        default at the next session start;
   2. otherwise (the skill's shell calls, the terminal command, `later all`)
      the stored copy (item 4);
   3. otherwise the default `LATER.local.md`.
4. **The stored copy.** The session-start hook and every module-started
   engine run store the value they resolved when it differs from the copy,
   replacing the copy atomically. The hook stores it before any of its early
   exits (a non-`startup` source, an agent start, an entry point other than
   the CLI), so a user who works only in the desktop app or an SDK host still
   gets a terminal that follows the setting. The copy lives at a fixed
   per-user path that the terminal command and the skill's shell calls can
   reach without any Claude Code variable, and outside any cache folder,
   because clearing a cache must never send notes to another file.
   Designer's call: under `${XDG_STATE_HOME:-$HOME/.local/state}/later/`.
5. **Validation.** A usable value is one file name: not empty, not `.` or
   `..`, no `/` or `\`, no glob characters (`*`, `?`, `[`), no control
   characters, at most 255 bytes. A glob would make `later all` read every
   matching file under the home folder as a queue. An unusable value is
   never stored and never used: the run falls back to the stored copy or the
   default, and the session-start message says so in one line at every
   session start while the setting stays unusable (designer's call: a broken
   setting stays visible). The README asks for a name no other tool uses,
   because the engine appends to and rewrites whatever file has that name.
6. **Changing the name moves nothing.** Queues under the old name stay where
   they are and are no longer listed, by any entry point or by `later all`.
   The README says so and shows how to rename them by hand. A queue under a
   new name is a new queue for the "new notes" display, whose state is keyed
   by the queue's path: its first session start announces its stamped notes
   once.
7. Worked example. Dana sets the queue file to `LATER.md` in `/config`.
   - Her next `/later` or pane refresh passes `LATER.md` to the engine, which
     stores it; her next session start would do the same.
   - In a terminal in `shop`, `later fix the docs` reads the stored copy and
     writes `shop/LATER.md`.
   - Her older `shop/LATER.local.md` is left as it is, and no entry point
     lists it any more.
   - Two Claude Code configuration folders on one account with different
     values follow whichever ran the engine last; the README asks for one
     value per person.

### R4. Git and the queue file

1. The engine writes nothing to `.gitignore`, `.git/info/exclude`,
   `core.excludesFile` or any other git configuration.
2. The README explains: the queue starts untracked; keep it private through
   the repository's `.gitignore`, the clone's `.git/info/exclude`, or a
   global excludes file; or commit it to share it. It warns that two people
   who park notes on separate branches get a merge conflict at the end of
   the file.

### R5. Engine portability

Targets: Linux with GNU tools; stock macOS (bash 3.2.57, BSD userland);
Git for Windows' bash (the engine only; its Windows entry points are 0.3.0).
Required programs: bash, git 2.31 or later (the engine uses
`--path-format`), and the POSIX tools the three platforms share. `jq` is no
longer required anywhere. `flock` stays optional.

1. **No jq.** The session-start hook reads its JSON input and writes its
   JSON output without jq. The output is valid JSON for any note text,
   including quotes, backslashes, tabs, carriage returns, other control
   characters and non-ASCII text (Georgian script is the owner's test case).
2. **Locking without flock.** Where `flock` is missing, writers serialize
   through a lock that works on the three targets (a directory created with
   `mkdir` is the expected shape). The 0.1.0 fallback (run unlocked) loses
   updates: in a local test, 8 parallel `done 1` calls closed one note, not
   eight. The lock behaves like the `flock` path towards its callers: a
   writer waits at most 5 seconds and then fails with the same message ("the
   queue is locked by another writer"), so the hook's and the module's
   10-second budgets hold. The lock records its holder's process id and is
   broken at once when that process is gone, and after a stale timeout
   otherwise, because the module's timeout can kill an engine that holds it.
3. **Line endings and BOM.** The engine reads a queue whose lines end in
   CRLF, or that starts with a UTF-8 BOM, exactly as it reads an LF file:
   dated notes keep their dates, `--if` comparisons match, and the BOM never
   hides a first-line note. Lines the engine does not change stay
   byte-identical; lines it adds end in LF (designer's call). The module's
   comments that assume the engine keeps a note's carriage return are
   rewritten with this change.
4. **Path spellings.** The comparison that keeps a git-tracked home folder
   from becoming every project's queue works when git and the shell spell the
   same folder differently (Git Bash prints `C:/Users/x` from git and
   `/c/Users/x` from `pwd -P`; a symlinked home on Linux or macOS does the
   same). The lock and state keys derive from the normalized path, and the
   key of an unchanged queue path on Linux stays what 0.1.0 computed. (A
   renamed queue file is a new path; see R3.6.)
5. **No GNU-only constructs.** Known instances in the baseline: `date -d`
   (stamp parsing and new stamps), `chmod --reference`, `find -xtype`,
   `mv -T`, `readlink -f` (missing before macOS 12.3), `sha1sum` (where
   missing, a fallback must give the same digest so existing state keys
   survive). The builder audits the rest of `later.sh` and `scripts/later`
   the same way.
6. **Process budget.** The number of processes an engine command starts does
   not grow with the number of open notes. This holds for `list`, `rows`,
   `add`, `done`, `drop` and `session-start`, and per queue for `all`.
   Reason: Git Bash costs 60 ms or more per process (more on machines with
   endpoint protection), the hook and the module allow 10 seconds, and the
   pane runs `rows` every five seconds. At 0.1.0 counts, `rows` on 100 notes
   starts about 414 processes. Stamp conversion keeps minute precision in
   local time: stamps are written in local time, and session-start counts a
   note as new when its stamp is at or after the minute of the last display.
   A conversion that treats stamps as UTC shifts every epoch by the zone's
   offset: in UTC+4 the notes parked up to four hours before the last display
   are announced again at every start, and in UTC-5 notes parked up to five
   hours after it are never announced.
7. **Terminal link hardening.** The terminal link step returns quietly when
   the plugin's own `scripts/later` is missing or not executable, instead of
   linking to it. It still runs only on Linux and macOS.
8. Everything else the baseline tests assert keeps holding, apart from the
   expectations this document changes (file name, setting names).

### R6. The session-start hook

`hooks/hooks.json` declares the hook with `"shell": "bash"` and the command
`bash "${CLAUDE_PLUGIN_ROOT}/scripts/later.sh" session-start`; matcher
`startup` and the 10-second timeout stay. Reason: the command no longer
depends on the execute bit or the shebang, and on a Windows machine without
Git Bash the field turns a PowerShell parse error into Claude Code's prompt
to install Git for Windows. The skill's shell commands stay as they are in
0.2.0.

### R7. Line endings in the repository

A root `.gitattributes` forces LF on checkout for all text files and names
the extensionless `scripts/later` explicitly, so a clone under Git for
Windows' default `core.autocrlf=true` still gets LF scripts. It contains no
`export-ignore` or `export-subst`.

### R8. Tests and CI

1. `tests/later.test.sh` runs on all three targets. GNU-only helpers in the
   suite (`md5sum`, `stat -c`, `mktemp -d -p`) are replaced. A case that
   cannot run on a platform (permission cases that rely on `chmod` and the
   symbolic link cases under Git Bash) is skipped there with a printed
   reason; no case passes without asserting.
2. New engine cases:
   - a CRLF queue and a BOM queue;
   - the resolution rule of R3 (option, stored copy, default; an unusable
     value; the copy refreshed by a run that receives the option);
   - the whole suite with no `jq` reachable by the engine;
   - parallel writers without `flock`: 8 parallel `add` keep 8 notes and 8
     parallel `done 1` close 8 notes;
   - without `flock`, a writer facing a held lock fails within 5 seconds
     with the refusal message, and a lock left by a killed writer is broken
     at once;
   - the "new notes" announcement under a zone other than UTC
     (`TZ=Asia/Tbilisi`): a note added at the test clock is announced at the
     next session start and not again at the one after (the suite otherwise
     runs under `TZ=UTC`, which cannot catch a zone error);
   - the process budget on Linux, comparing the process count of `rows`,
     `list` and `session-start` at 5 and 100 notes.
3. `hooks/register.test.ts`: the module passes the `file` setting to every
   engine run; the existing tests keep passing, with the assertions on the
   exact run options widened to the added environment.
4. A GitHub Actions workflow runs on every push and pull request to `main`,
   one job per runner:
   - **ubuntu-latest**: `claude plugin validate . --strict`,
     `claude plugin test .`, `tests/later.test.sh`, shellcheck on the
     scripts. The TypeScript type check stays a local check (designer's
     call): its declarations are written only by an interactive session that
     loads the plugin folder, they are not committed, and CI has no
     signed-in session.
   - **macos-latest**: `tests/later.test.sh` with the engine's PATH limited
     to `/usr/bin:/bin:/usr/sbin:/sbin`. Test helpers may call other tools by
     absolute path; the engine may not.
   - **windows-latest**, `shell: bash`: `core.autocrlf` left at the runner's
     default; the job first asserts that git checked the scripts out with LF
     (`git ls-files --eol`), then runs `tests/later.test.sh`.
   Claude Code is installed in CI at the version floor, 2.1.296.
   `claude plugin validate` and `claude plugin test` need no sign-in (checked
   locally on 2.1.300 with an empty configuration folder).

### R9. README

The root README is the plugin's README. It is longer than 40 words, and it
describes everything the plugin runs, sends and writes. It covers:

1. What Laterbox is, with the commands a user types.
2. Install: from a terminal (`claude plugin marketplace add
   akalongman/claude-laterbox`, then `claude plugin install
   laterbox@akalongman`) and inside a session; the team variant with
   `--scope project`.
3. Requirements per platform:
   - **Linux**: bash and git 2.31 or later; Debian and Ubuntu, Fedora, and
     BusyBox-based systems such as Alpine (install bash and git; untested,
     because CI runs no BusyBox target).
   - **macOS**: git (from the Xcode command line tools); nothing from
     Homebrew.
   - **Windows (native, PowerShell)**: not supported yet, planned for a later
     release; use WSL.
   - **WSL**: the Linux rows apply. Use one environment per project, keep
     the project inside the WSL file system, and never park notes into one
     queue from WSL and from native Windows: their locks do not see each
     other.
4. That the plugin needs Claude Code (2.1.296 or later), and that `/later`
   and its pane run in the terminal CLI. The module API marks its process
   calls "CLI only"; the desktop app is untested.
5. Disclosures:
   - the rewrite: `haiku` (default) sends the newest messages of the
     conversation, as an excerpt, to a small model; `fork` runs the session's
     own model over the whole conversation; `off` sends nothing;
   - what it writes: the queue file at the project root (the main checkout
     for a worktree), the data folder, the state under `~/.cache/later/`, the
     stored setting under `~/.local/state/later/`, and the link
     `~/.local/bin/later`, which lives outside the plugin folder and which
     `laterbox.terminal` set to `off` removes;
   - no other network access than the model calls the rewrite makes through
     Claude Code.
6. The git choice of R4.
7. A settings table: `rewrite`, `terminal`, `file` (with the advice to pick
   a name no other tool uses).
8. Uninstall: what stays behind (the link unless `terminal` was set to `off`
   first, the state folders, the queue files).
9. The develop section with root paths.

### R10. Switch-over on the owner's machine

The owner's machine runs 0.1.0 today, and a live check of 0.2.0 beside it
cannot pass: both modules would register `/later`, the terminal link would
stay with 0.1.0, and the terminal command would run 0.1.0's engine against
`NOTES.local.md`. So the owner's machine switches to 0.2.0 after the
implementation and before the verification, with no outward step involved.

The builder writes a one-off script for it, kept in the owner's private
repository and not in this one (designer's call). It has a dry run that
prints every action, and a reverse mode that restores the 0.1.0 names and
install. The builder tests it on a copied tree first; the owner runs it.
Its steps:

1. Close or reload every session that has `later@akalongman` loaded, so no
   0.1.0 hook or module recreates an old queue file in the meantime.
2. For each Claude Code configuration folder on the machine that has the
   plugin: uninstall `later@akalongman`, remove the marketplace `akalongman`.
3. Remove `~/.local/bin/later` when it is a link into a `later-*` or
   `laterbox-*` data folder (the second covers a `laterbox-inline` link left
   by a `--plugin-dir` test session); leave any other file alone.
4. Rename every `NOTES.local.md` queue under the owner's project folders to
   the new name, refusing where the target already exists. One of the
   owner's 25 queues has a hand-written heading, so the script does not
   select files by their heading. Each renamed queue announces its stamped
   notes once at its first session start (R3.6).
5. Move the local checkout to the folder named after the new repository. Its
   remote changes with the GitHub rename in R11.
6. Add the marketplace from the moved folder and install
   `laterbox@akalongman` in each configuration folder. A folder marketplace
   runs the checkout itself, so this install is the release under test.
7. After the release, repeat steps 3 and 4 on any other machine that holds
   queues.

The owner's own agent instructions and dotfiles name `NOTES.local.md`,
`later:notes` and the old repository. Their edits are proposed to the owner
separately and are not part of this release.

### R11. Release

1. The release commit sets `version` to `0.2.0`. `63d4208` is published with
   it.
2. Outward steps, in order, each the owner's to approve: rename the GitHub
   repository; point the checkout's remote at the new URL; push `main`; watch
   the workflow on `main` to green on all three runners; tag `v0.2.0`
   (designer's call); the owner submits in the developer portal.
3. The macOS and Windows jobs first run on that push. A failure there blocks
   the tag and the submission and is fixed forward on `main` (designer's

   outside it).

## Known risks

- The "LaterBox" iOS app may cause a brand hold.
- The hooks module API is early access; process, file and command semantics
  may change between Claude Code releases. The version floor is pinned and
  CI runs `claude plugin test` on every push.
- The macOS runner is a recent macOS. Users on older releases may lack
  tools the runner has; R5 avoids `readlink -f` for that reason, and the
  builder avoids other recent additions the same way.
- An install from the directory's own marketplace gets a different data
  folder and, if a `later` link from another install exists, the existing
  "refused" notice. This is the baseline behaviour and stays.
