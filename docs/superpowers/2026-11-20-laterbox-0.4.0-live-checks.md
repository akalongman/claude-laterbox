### F2: `items.pattern` in a live request

The floor probe of Task 3 cannot discriminate: at Claude Code 2.1.296 the
tool was listed with schemas deliberately broken as well
(`task-3-report.md:77-83` in the run's working folder), so it shows only
that registration does not refuse `items.pattern`.

The first live use of the schema was this run's first working-copy model

after 34ms" and "Dynamic tool loading: 0/40 deferred tools included" on

result event reads `success`, with `is_error` false and
`api_error_status` null; no other line of the stream holds `api_error`.
Every later working-copy session offered the same tool and called it with
no tool search, and every id the model sent matched the pattern.

Not observed: whether Claude Code passes `pattern` on into the tool
definition it sends to the API. The module registers the schema with it
(`hooks/tool.ts:53`), and the debug log shows the tool served at a local
address ("1 tool(s) served at 127.0.0.1"), but no saved file shows the
request: the start event lists tool names only, and no saved stream,
start event or debug excerpt holds the pattern `^[0-9a-f]{8}$`. The full
debug log was deleted, and its excerpt keeps only the lines naming
laterbox and the deferred tool counts, so the absence of an API error
rests on the result event, not on the log.

Verdict: pass. A tool whose registered schema carries `items.pattern`
works in a live session with this model, on Claude Code 2.1.329 and
2.1.330: it was offered and called in every working-copy session, and
check 3.1 ended with no API error. That the API itself received and
accepted `pattern` is not shown, since the request was not seen. Whether
the API also holds the model's output to the pattern is not shown either:
no session sent an id outside it.

Per call, input and result characters: 0.3.2: list 17 and 21,225, drop 564
and 543, drop 559 and 538, done 578 and 555. 0.4.0: list 17 and 4,887, done
36 and 126, drop 47 and 259.

The sums were made with this `jq` program over each stream
(`jq -s -f sums.jq <stream>`), after it gave the right answers on a
hand-made stream that held a repeated call and both result shapes
(`sums-probe.jsonl`, `sums-probe-result.json`):

```jq
def result_text:
  if (.content | type) == "string" then .content
  elif (.content | type) == "array" then [.content[] | select(.type == "text") | .text] | join("")
  else "" end;

([.[] | select(.type == "assistant") | .message.content[]?
   | select(.type == "tool_use" and .name == "mcp__laterbox__queue")]
   | reduce .[] as $use ([]; if any(.[]; .id == $use.id) then . else . + [$use] end)) as $uses
| ([.[] | select(.type == "user") | .message.content[]? | select(.type == "tool_result")]
   | map({key: .tool_use_id, value: result_text}) | from_entries) as $results
| {
    calls: ($uses | length),
    list_calls: ($uses | map(select(.input.action == "list")) | length),
    actions: ($uses | map(.input.action)),
    per_call: ($uses | map({id, action: .input.action, input_chars: (.input | tojson | length),
                            result_chars: (($results[.id] // "") | length)})),
    input_chars: ($uses | map(.input | tojson | length) | add // 0),
    result_chars: ($uses | map(($results[.id] // "") | length) | add // 0)
  }
| .total_chars = .input_chars + .result_chars
```

Input characters are each call's input as compact JSON; result characters
are the result's text; `jq` counts code points.

Both runs closed the same three notes: their queue files afterwards are
byte for byte the same, with note 7 ticked, notes 12 and 31 gone and the
other 37 open notes in their order. So the comparison is like for like in
