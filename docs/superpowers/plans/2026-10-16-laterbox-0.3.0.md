# Laterbox 0.3.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `/later`, the pane, the skill and the session-start line work on native Windows in the Claude Code CLI, quickly, with no console window, no setup, and a plain line for every failure.

**Architecture:** The one bash engine stays the only writer. On Windows the hooks module finds Git for Windows' `bash.exe` without starting a process and runs the engine through it; user text reaches the engine on standard input on every platform; the pane reads the queue only when it changed; the skill reaches the engine through a tool the module registers. Pure logic (the bash search, the refresh decision, the failure kinds, the tool's input) lives in small files under `hooks/` with no `$`, so it is tested without a Windows host.

**Tech Stack:** bash (3.2 compatible), git 2.31+; TypeScript hooks module on the Claude Code mod API (floor 2.1.296); GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-10-16-laterbox-0.3.0-design.md` (amends `docs/superpowers/specs/2026-10-15-laterbox-0.2.0-design.md`).

## Global Constraints

- Every constraint of the 0.2.0 plan's Global Constraints still holds (names, bash 3.2, no GNU-only flags, no jq, `later:` prefix, `laterbox.<key>` settings, TypeScript rules, shellcheck clean, no em or en dashes, agent-neutral prose).
- Claude Code floor stays 2.1.296: its types (`claude-code.d.ts` written by 2.1.296) declare every API this plan uses (`$.env.get`, `$.fs.exists`, `$.fs.stat`, `$.session.cwd`, `$.clock.now`, `$.tool.register`, the `tool.call` and `tool.check` events).
- `$` is passed only to functions declared at the top level of `hooks/register.tsx`. The new files `hooks/bash.ts`, `hooks/gate.ts`, `hooks/failure.ts` and `hooks/tool.ts` never touch `$`, `on` or any engine noun: the directory refuses a mod whose `$` it cannot follow.
- `$.env.get` takes string literals only: `'OS'`, `'SHELL'`, `'CLAUDE_CODE_GIT_BASH_PATH'`, `'ProgramFiles'`, `'ProgramW6432'`, `'ProgramFiles(x86)'`, `'LOCALAPPDATA'`, `'PATH'`.
- The engine recognises Git Bash by `OSTYPE` (`msys*` or `cygwin*`) and never starts `uname` for it.
- The 4.1 line, verbatim: `laterbox: Git for Windows' bash was not found. Install Git for Windows (https://git-scm.com/download/win) and restart Claude Code.`
- Work stays on `main`, committed locally only. **Never push**: the directory review of 0.2.2 tracks `main`, and a push reaches it within minutes. Never create, switch or rename a branch. Commits are signed by the repository's configuration, path-limited (`git add <paths> && git commit -m "<title>" -- <paths>`), imperative title under 72 characters, no trailers; verify each with `git show --stat HEAD`.
- Gates for every task that touches code: `claude plugin validate . --strict`, `claude plugin test .`, `bash tests/later.test.sh` (ends `0 failed`), `shellcheck scripts/later scripts/later.sh tests/*.sh`, `npx -y -p typescript@5.9.3 tsc -p . --noEmit`.

## Review Focus

1. Note text that is empty or only whitespace on standard input: `later: nothing to park (empty note)`, nothing written. Test in Task 1.
2. A Windows `PATH` with quoted entries (`"C:\Program Files\Git\cmd"`), empty entries (`;;`) and trailing backslashes: the scan of 1.3 step 5 still finds bash. Test in Task 4.
3. A plugin root or project path with non-ASCII letters (`C:\Users\ნინო\...`): the script path, the `rows` path and the note on standard input round-trip byte for byte. Tests in Tasks 2 and 4; live in Task 12.
4. The queue file deleted while the pane is open: the next tick reads, and the pane shows an empty queue, not an error. Test in Task 7.
5. The tool called with a number that is zero, negative, fractional or a string, or with `text` missing: refused with a reason, no engine run. Test in Task 8.

### Task 8: The queue tool and its permission answer

**Files:**
- Create: `hooks/tool.ts`, `hooks/tool.test.ts`
- Modify: `hooks/register.tsx` (`session.start`, two new hooks), `hooks/register.test.ts`

**Interfaces:**
- Consumes: `runEngine($, context, args, input?)` (Tasks 3, 5).
- Produces:
  - `export type ToolRequest = { readonly action: 'list' } | { readonly action: 'add'; readonly note: string } | { readonly action: 'done' | 'drop'; readonly number: number; readonly text: string }`
  - `export function parseToolInput(input: unknown): { readonly ok: true; readonly request: ToolRequest } | { readonly ok: false; readonly reason: string }`. Reasons, verbatim: `action must be list, add, done or drop`; `add needs a note that is not empty`; `done and drop need a whole note number of 1 or more and the note's text`. `number` must satisfy `Number.isInteger(n) && n >= 1`; `note` and `text` must be strings, `note` non-empty after trimming, `text` non-empty as given. Keys other than the four (the call's reserved `tool`, `tool_use_id`, `consent`) are ignored.
